So what.

The point of the code is not the script. It is a repeatable check that says what looked wrong, what you compared, what you concluded, and whether a retry is allowed. The data is synthetic: I work in dental billing, and these are practice projects for a technical operations role.

[01]

Payment Failure Investigation

Does the ledger agree with the last event for this id?

The break is one payment id whose ledger status and event log do not say the same thing.

SQL puts those two records side by side on one key. The investigate query returns the ledger row and the event rows for the same entity_id, in time order. On the disbursement ledger, the named queries load one disbursement by disbursement_id, the other rows that share its idempotency key, the other rows that share its trace number, and the events for that same id. The dental exception view compares a payment attempt with a posted payment on the same attempt id, and with posted payments that already use that idempotency key.

patterns/investigate/python/run.py prints the mismatch in one sentence and does not update either side. investigate_failure.py prints the timeline and a cause label. It does not retry. investigate.py prints the dental exception queue and writes exception_queue.csv. It does not change payments.

So what: you read that sentence before you pick an action, and you leave the payment unchanged until a later script says a retry is allowed.

[02]

Duplicate Payment Risk After a Timeout

Did this disbursement already move, or is it safe to send again?

The break is a timeout that looks like a failure while the same idempotency key is already settled on another row.

SQL compares the failed attempt with every other record that carries that key. The disbursement query returns every row with the same idempotency key. The dental view compares the attempt with posted_payments on that key. The repair query flags a failed attempt when a posted payment with that key is already settled.

reprocess.py blocks the row as idempotency_already_settled when another row on the key is settled or posted. It plans a retry only when the amount matches, there is no return, and no settled row uses the key. reprocess_plan.py blocks status_failed_but_settled and blocks a retry whose key is already posted. If the SQL view marks a row safe and the key is already posted, the script refuses to write the plan. patterns/repair/python/run.py refuses the settled key and plans the open key. --execute writes a plan row, not a payment.

So what: do not resend a key that is already posted.

[03]

Rejected Batch Investigation

Was this row rejected for bad data, or can it be sent again?

The break is a batch row the file rejected before it went out, so sending the same file again rejects it again.

SQL loads the disbursement and the events for that disbursement_id. The reconcile query selects settled disbursements for one client whose trace number is present, and the script compares those rows with the client CSV on the same trace, after it checks the file header against the expected columns.

investigate_failure.py labels the row batch_rejected when the status is rejected, or an event is batch.reject, or the code is BATCH_REJECT. classify_webhook.py labels BATCH_REJECT as fix the recipient and does not build a new file. reprocess.py blocks a rejected status as fix_before_retry. reconcile_batch.py reports matched, missing from the batch, in the file but never settled, amount mismatch, and duplicate trace. It does not repair fields.

So what: you fix the recipient data that caused the reject, and you leave the rejected row off the retry plan.

[04]

API & Integration Failure Triage

What should this processor code make a person do?

The break is a webhook or batch-reject line that still needs a label before anyone sends, waits, or escalates.

SQL looks the code up. The classify query returns the action on the code map, and it returns escalate when the code is not on the map. The disbursement script reads the JSONL event itself. It does not call a live API. investigate_failure.py prints the HTTP status from that log next to the code.

classify_webhook.py decides the label. A parse error escalates. R02, R03, R04, and BATCH_REJECT mean fix the recipient. Other return codes wait. Codes 91 and 96 are retry. Settled or posted means do not retry. Code 00 with submitted or pending means do not retry. Anything else in that set escalates. The script does not retry, refund, or edit a recipient. patterns/classify/python/run.py prints the label only. Unknown codes, including the sample XX, escalate.

So what: you follow the label, and a retry label still has to pass reprocess.py before you plan a send.

[05]

Pending Payment with a Completed Provider Status

The row is still open. Did the provider already complete it?

The break is an internal row that is still failed or pending while the provider event for that same id already says settled.

SQL joins the two records on the payment id. The disbursement query webhook_settled_row_not_settled joins the disbursement to its webhook on disbursement_id and keeps the pair when the webhook says settled and the ledger status does not. The dental view joins the attempt to a posted payment on attempt id when the attempt says failed. The toolkit query compares ledger status with the last event status for one entity_id.

investigate_failure.py labels that pair status_mismatch. reprocess.py blocks it as webhook_already_settled when a webhook says settled or posted and the row itself is not. The planted row is failed. The same block covers a pending row. reprocess_plan.py blocks the dental case as status_failed_but_settled. The investigate script prints the mismatch and does not update either side.

So what: you do not send that payment again. The provider already completed it, so you correct the internal status or you leave the row.

[06]

Payment Failure Rate Analysis

Proposed approach

Which slice of attempts failed more often than its own baseline?

The break is a failure count with no baseline, so a busy client and a worsening code look the same.

The SQL would group attempts by client, method, processor, time window, or error code, divide failures by attempts in that window, and compare the rate with the same slice’s earlier window. This repo does not run that query.

No script here writes a failure rate. patterns/variance/python/run.py is the nearest file, and it answers a dollar question. Its query subtracts expected cents from actual cents and flags a gap larger than that line’s tolerance. The script prints the dollars. A failure-rate percentage is not in its output, and this page does not treat a simulated dollar gap as a rate.

So what: you do not change a retry rule from a rate this repo never produced. You use the variance script when the question is a dollar gap.

[07]

ACH Return Investigation

Does this return mean wait, or fix the account?

The break is a return code already on the disbursement or in its log. Another send to the same account repeats it.

SQL returns the disbursement row and the events for that disbursement_id, including the processor code on each. The comparison is that code on the row against the same code on the log, and a return event against a ledger status that is not yet returned.

reprocess.py blocks a return that is not R02, R03, or R04 as return_already_received. R02, R03, and R04 become fix_recipient_data, so they are not planned. classify_webhook.py labels those three codes as fix the recipient and other return codes as wait for the return window. investigate_failure.py labels R01 and R03 as their own causes, and it labels a return sitting on a row that is still failed as return_in_flight. These labels are this demo’s policy.

So what: you wait out an insufficient-funds return instead of retrying it the same day, and you fix the account when the code says it cannot be located. Neither row goes on the plan.

[08]

Client Configuration Validation

Proposed approach

Do this client’s settings match the approved profile?

The break is a new client whose stored settings disagree with the approved profile, so the first batch fails for a setting.

The SQL would compare the client’s stored settings with the approved profile on client id: account, method, and limits. This repo has no profile table and does not run that comparison.

The script would run one controlled transaction and write down what it did. There is no such script in this repo, and there is no result to read.

So what: you do not approve the client from this repo, because the check has not been run.

[09]

Batch-to-Ledger Reconciliation

Which traces match, and which ones do not agree?

The break is a trace that is missing on one side, doubled, or carrying a different amount on the client file than on the settled ledger.

SQL joins the two sources on trace. The reconcile query labels each trace matched, missing on the left, missing on the right, amount mismatch, or duplicate key. reconcile_batch.py groups settled disbursements for one client, status settled, by trace number, and groups the CSV on that same trace. The dental view compares a posted payment with its claim on claim_id, including a payment whose patient id is not the claim’s patient, and it compares ERA amount with insurance responsibility on that claim.

reconcile_batch.py stops if the CSV header is not the expected columns, then reports those buckets. It does not repair fields. patterns/reconcile/python/run.py prints the label and does not change either source. investigate.py writes those dental rows to the exception CSV, and the short-pay row carries the action to appeal or rebill. reprocess_plan.py never takes that reason as a retry candidate. Dollar figures for these breaks are the simulated findings already on the case pages.

So what: you work the bucket the script named, and you appeal a short pay instead of retrying the card.

[10]

Automating Recurring Exception Checks

Can this check run again without creating a second payment?

The break is the same exception coming back every day, where a hand-built retry is how a settled key gets sent twice.

SQL repeats the same comparison on every run: the attempt’s idempotency key against posted or settled payments, and the disbursement’s key against other rows that are already settled or posted.

patterns/repair/python/run.py is a dry run unless you pass --execute. It refuses the settled key, plans the open key, and on execute inserts one plan row while the posted-payment count stays the same. reprocess_plan.py and reprocess.py are that control on the two ledgers. --execute writes a queue row and does not create a payment. investigate.py rewrites the exception CSV from the SQL view every time it runs.

So what: you rerun the script and queue only the rows it marked safe. You do not type a retry for a key the script blocked.

Financial exceptions, two systems

The same break.

Ten ways money fails to tie. A dental ledger and a disbursement file ask the same questions. Haley Maes.

These are the kinds of breaks the work is built to catch. Every row is synthetic. Nothing on this page is a confirmed live incident.

[01]

Unclear failure

A payment fails, and the reason on the row is not enough to act.

Read the ledger with SQL. Set the API or JSON log beside it. Compare a success with this failure and say the difference in one sentence.

patterns/investigate does that for one id. The SQL returns the timeline. investigate_failure.py does the same on the disbursement ledger, with the disbursement queries. Choice ops.

[02]

Duplicate after a timeout

The first attempt timed out, a second send goes out, and the idempotency key is already settled.

Look up the key before any retry. If it already settled, block the second payment.

reprocess.py blocks that case on a dry run. reprocess_plan.py refuses a dental post whose key is already posted. Payment exceptions · Choice ops.

[03]

Whole batch rejected

The file is rejected, so none of the rows in it move.

Validate the fields before reprocessing. A bad or missing field is fixed, then the row goes out in a new file. Reconciliation is the step after that file is worth comparing.

reconcile_batch.py is that next step. It compares the Northwind file with settled disbursements, and it stops if the columns are not the expected header. Choice ops.

[04]

Integration stops

A client change lands and the integration stops.

Check the HTTP code, the auth result, and whether a JSON field is missing or renamed. The next action is a label. It is not a live call.

patterns/classify maps a code to retry, do not retry, fix data, wait, or escalate, and prints the label only. Pattern notes.

[05]

Stuck pending

The internal status stays pending while the provider already shows completed.

Compare the internal status with the webhook. If the webhook settled, correct the row in place. Sending it again pays twice.

The planted status mismatch on Choice ops is $1,250. investigate_failure.py sets that row next to the event log.

[06]

Failure rate jumps

Failures take a larger share of attempts than they did.

The question a query has to answer is which slice moved (client, method, processor, time window, or error code) and by how much against its own baseline. Group the attempts, compare the slices, and name the outlier.

That is the same style of aggregation as patterns/variance: expected against actual, then the gap. The variance script flags a business total outside its tolerance and prints dollars. It does not produce a failure-rate percentage. Pattern notes.

[07]

ACH return, days later

The payment looked finished, then a return shows up days later.

Read the return code before anyone retries. R01, insufficient funds: do not retry the same debit. R03, account not located: fix the recipient, and do not send the same token again.

Both are already on Choice ops. R01 is $480. R03 is $915.50. classify_webhook.py turns the code into a label.

[08]

New client, wrong configuration

A new client is configured, and a setting does not match the profile that was approved.

Compare the settings with that approved profile. Run one controlled transaction. Write down what it did. This repo has no result from that test to quote.

[09]

Two reports disagree

Two reports that should describe the same money do not.

Match on id and on amount. Separate the rows that match, the rows missing from each side, an amount that does not agree, and a key that appears twice.

The Northwind file on Choice ops, from reconcile_batch.py: matched 3 / $1,650; missing TR-9101 $200; not sent TR-9102 $150; amount mismatch $300 vs $280 (TR-9103); duplicate trace $128 vs $64 (TR-9104). Payment exceptions is the dental version of the same match. The short form is patterns/reconcile.

[10]

The same manual fix

The same check gets done by hand every day.

Turn the check into a script. Default to a dry run. Refuse the row when its key is already settled.

patterns/repair does that. --execute writes a plan row and does not create a payment. Pattern notes.

The kind of dental break

The same shape, on a practice ledger. A name is not a result.

  • Insurance underpay against the fee schedule.
  • A procedure downgraded: scaling and root planing submitted as one code and paid as another.
  • Payment posted to the wrong patient.
  • Claim never reached the payer, because the clearinghouse rejected it.
  • Duplicate post.
  • Payment applied to the wrong procedure.
  • Contractual write-off that does not match the fee schedule.
  • Production is not collections.
  • Insurance accounts-receivable aging.
  • Bank deposit against the practice-management total: timing, or money that is missing.
  • One payer is the denial-rate outlier.
  • Two records for the same name.
  • A month-end total that changes after close, from voids, refunds, or posting date versus service date.

Dollar figures on this page are the synthetic cases already published with the drills.

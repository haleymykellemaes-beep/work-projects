Payment Exception Playbook

Ten payment exception scenarios connecting dental billing experience with technical operations workflows.

These synthetic examples show how I would investigate failed payments in a technical operations role. I work in dental billing. I built the practice projects in this repo. A scenario below is implemented only when a script in this repo demonstrates the check. The other two are a proposed approach.

[01]

Payment Failure Investigation

Implemented. Read the ledger and the event log for one id, and say how they differ.

patterns/investigate loads PAY-1042. The SQL returns the ledger row, then the events. The ledger says failed. The last webhook says settled. The script prints that sentence and does not update either side.

investigate_failure.py does the same job on the disbursement ledger: JSONL beside the SQLite row, using the disbursement queries. investigate.py prints the dental exception queue from the SQL view and writes a CSV. It does not change payments. Reconciliation · Disbursements.

[02]

Duplicate Payment Risk After a Timeout

Implemented. A timeout is not permission to send again. The check is whether that idempotency key is already posted.

DSP-7007 failed with code 96. DSP-7008 already settled $1,800 on the same key. reprocess.py blocks DSP-7007 as idempotency_already_settled. DSP-7011 is also a timeout, code 96, HTTP 504, $410, and it is eligible only because the amount matches, there is no return, and no settled row uses that key.

On the dental ledger, a patient-card attempt can say failed with processor code timeout after the webhook posted the same key. That planted case is $82. reprocess_plan.py blocks status_failed_but_settled and blocks a retry whose key is already posted. If the SQL view marks a row safe and the key is already posted, the script refuses to write the plan. patterns/repair refuses KEY-SETTLED and plans KEY-OPEN. Reconciliation · Disbursements.

[03]

Rejected Batch Investigation

Implemented. DSP-7004 is a rejected check-batch row, $220. investigate_failure.py labels it batch_rejected. The planted note says the file rejected the row before mail because the mail-to name was missing. classify_webhook.py labels BATCH_REJECT as fix the recipient. That label does not build a new file.

reprocess.py blocks a rejected status as fix_before_retry. reconcile_batch.py is the later compare: it checks that the CSV header matches the expected columns, then reports matched, missing from the batch, in the file but never settled, amount mismatch, and duplicate trace. It does not repair fields. Disbursements.

[04]

API & Integration Failure Triage

Implemented. The demonstrated check is a label for a webhook or batch-reject event. It is not a live call.

classify_webhook.py reads the JSONL. A parse error is escalate_to_engineering. R02, R03, R04, and BATCH_REJECT are fix the recipient. Other return codes wait. Codes 91 and 96 are retry. Status settled or posted is do not retry. Code 00 with submitted or pending is do not retry. Anything else in that set escalates. The script does not retry, refund, or edit a recipient. investigate_failure.py prints the HTTP status on the timeline next to the code. It does not test credentials.

patterns/classify looks the code up in SQL. Unknown codes, including the sample XX, escalate. Labels only. Toolkit.

[05]

Pending Payment with a Completed Provider Status

Implemented. If the provider event already says settled, do not send again.

DSP-7001 is failed on the ledger and settled on the webhook, $1,250. investigate_failure.py labels it status_mismatch. reprocess.py blocks any candidate whose webhook says settled or posted while the row itself is not. The planted row is failed, not pending. The same guard covers a non-settled row, including pending.

The dental queue has the same shape at $82: the attempt says failed and the card webhook already posted the key. reprocess_plan.py blocks it. patterns/investigate is PAY-1042, ledger failed, last event settled. Disbursements.

[06]

Payment Failure Rate Analysis

Proposed approach. The question is which slice of attempts moved (client, method, processor, time window, or error code) and by how much against its own baseline. This repo does not compute that rate.

patterns/variance is the nearest script, and it answers a different question. It subtracts expected dollars from actual dollars and flags a gap larger than a tolerance: collections, fees, and hours priced at $45. It prints dollars. It does not produce a failure-rate percentage. Toolkit.

[07]

ACH Return Investigation

Implemented. Read the return code before anyone plans a retry. The labels below are this demo’s policy, not a universal banking rule.

R01, insufficient funds, is already on DSP-7002, $480. reprocess.py treats a return that is not R02, R03, or R04 as return_already_received. classify_webhook.py labels those other return codes wait_for_return_window. The planted note says a same-day retry will not make the debit good. DSP-7009 is still failed on the ledger while an R01 return is in the log. The reprocess script blocks it. The investigate script labels it return_in_flight.

R03, unable to locate the account, is DSP-7003, $915.50. Both scripts label it fix the recipient. The planted note says another send to the same token fails the same way. R02 and R04 use that same fix-recipient label in this demo. Disbursements.

[08]

Client Configuration Validation

Proposed approach. Compare the client’s settings with the approved profile, run one controlled transaction, and write down what it did. This repo has no result from that test.

[09]

Batch-to-Ledger Reconciliation

Implemented. Match on trace and on amount. Separate rows that match, rows missing from each side, an amount that does not agree, and a trace that appears twice.

The Northwind file from reconcile_batch.py: matched 3 / $1,650; missing TR-9101 $200; in the file but not sent TR-9102 $150; ledger $300 vs file $280 (TR-9103); duplicate trace file $128 vs one settled $64 (TR-9104). Reconciliation is the dental version: posted payments against claims, including duplicate keys, a short pay, and cash on the wrong patient. The short form is patterns/reconcile.

[10]

Automating Recurring Exception Checks

Implemented. Turn the check into a script. Default to a dry run. Refuse the row when its key is already settled. Write a plan row. Do not create a second payment.

patterns/repair does that on two attempts. --execute inserts one plan row and leaves the posted-payment count unchanged. reprocess_plan.py and reprocess.py are the same control on the two ledgers. investigate.py rewrites the exception queue from the SQL view each time it runs. Toolkit.

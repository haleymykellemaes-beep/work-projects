Disbursement Investigation & Retry Controls

Did this disbursement already move, or is it safe to send again?

These synthetic examples show how I would investigate failed payments in a technical operations role. I built this practice project for this portfolio. All of the clients, recipient tokens, and traces are synthetic.

What I built

seed.py rebuilds a SQLite ledger, a JSONL webhook log, and one client batch file. investigate_failure.py prints the ledger row beside that log and names the cause. reprocess.py is a dry run. --execute inserts a plan row into reprocess_queue and does not create a second payment. It does not call a processor. It checks the key, the status, and the amount again before it writes, and it stops if the disbursement table changes size. reconcile_batch.py compares settled rows with the batch CSV. classify_webhook.py turns a processor code into a label. A label is not a send. The queries live in sql/disbursements.sql.

Sample output

Internal status says failed or pending, and the provider event says settled: do not send again. DSP-7001 is the planted case. The ledger says failed. The webhook says settled. The amount is $1,250. reprocess.py blocks it as webhook_already_settled.

Safe plan 3 payments / $637.50. Blocked 9 / $6,905.50. These are simulated findings.

A row is eligible only when every check in reprocess.py passes. The idempotency key is not already on another settled or posted row. No return is on the row or in the log. Every logged amount matches the ledger amount. The trace number is not already on another disbursement. No webhook already says settled or posted. Status is failed, or pending and last updated before the 24-hour window (the clock in this demo is 2026-11-15T17:00:00Z). Rejected rows are blocked until the data is fixed. Submitted rows stay in flight. Pending rows inside the window stay blocked. This script does not filter by payment method.

Code 96 and code 91 are not a pass by themselves. classify_webhook.py labels both as retry. reprocess.py still runs the checks above. DSP-7011 and DSP-7012 pass, so they are on the plan. DSP-7010 is also code 96 and is blocked because the acknowledgement is $755 and the ledger is $750. DSP-7007 is code 96 and is blocked because the same key already settled on DSP-7008 for $1,800.

ACH handling here is this demo’s policy, not a universal banking rule. R01, insufficient funds, is a return already received: the plan blocks it and the webhook label is wait. A same-day retry is not treated as a way to make the debit good. R03, unable to locate the account, is fix the recipient: do not send the same token again. R02 and R04 use that same fix-recipient label. Any other return code is blocked as a return already received.
